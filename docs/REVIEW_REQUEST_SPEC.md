# Exact-version review requests

Kevin requested this feature on 2026-11-17 after the exact-version review queue landed in PR 454. The conductor needs to know who was asked to review a submission before a verdict exists. A reviewer starting a fresh session needs to recover the exact target and evidence from Athena.

## Command and storage

Add `POST /issues/{review_issue_id}/review-requests` and conductor/full MCP tool `request_candidate_review(review_issue_id, candidate_id, reviewer_id, idempotency_key=None)`. Use an existing review issue. Require strict positive signed-64-bit IDs and forbid additional body keys. The bounded success receipt contains request_id, review_issue_id, candidate_id and reviewer_id. It excludes candidate identity, report and profile data. Normal scoped/run-bound HTTP idempotency applies, including historical replay. A fresh duplicate of the same latest, current issue/candidate/reviewer tuple returns the same receipt without another event, even during pickup. Revalidate authority and visibility on fresh calls.

One additive forward-only migration creates `issue_review_requests` with monotonic id, candidate_id, review_issue_id, reviewer_id and unique request_event_id, foreign keys, indexes for issue/candidate/reviewer lookups, and uniqueness of (review_issue_id, candidate_id). Immutable rows reference a matching, native `review_requested` issue activity and protect that event from edits/deletion. Keep the event detail generic so existing activity feeds cannot disclose a hidden target or reviewer. These operational associations are outside selective portability and retained by full DB recovery. Existing reviews get no requests retroactively.

The command owns a single clean BEGIN IMMEDIATE. Re-read the authorized requester using current issue-write policy on the review issue. Require visibility of the current source issue and original candidate completion event. Both issues must be distinct, non-archived, in the same non-null project; candidate must be canonical current. The named reviewer must be an active writing account distinct from the submitter, already an assignee or delegated contributor on the review issue and able to read both roots and the recorded candidate event. The command grants no membership, assignment or lease. Missing/invisible targets use a uniform refusal. A new request requires an open (non-done) review issue with no active possession. Check conditions and record generic activity plus association atomically. Return conflicts without side effects.

A review issue has at most one outstanding target. For this first release it may be reused for a new candidate on the same source issue after its previous request was fulfilled or superseded and its lease is free. Refuse a different reviewer on the same issue/candidate and rebinding a review issue to a different source. Require access to the prior request and original target before comparing or changing that binding; hide prior identity in conflicts. A conductor needing another independent reviewer may use another review issue. Multiple requests against one candidate are legitimate. A pre-existing linked review on the same issue/candidate cannot be retroactively claimed as fulfillment. Ordinary unrequested review issues keep their current behavior.

## Reads and completion

Compute facts from requests, existing leases, current candidates and native completed reviews. `requested` means an outstanding current request. `picked_up` means its named reviewer currently holds an active lease on its review issue. Issue one only while the issue is free so a pre-existing possession cannot be attributed to a new request. `fulfilled` requires a later exact candidate review on that review issue by that reviewer. A replacement submission supersedes outstanding requests for the old candidate, including same-content replacements. Preserve the exact candidate/review linkage. Make lease ownership visible separately from supersession so a fresh reviewer holding A can see A was replaced. Already fulfilled historical requests retain their completion. Active possession is an observation at the read clock. Unrelated leases or ordinary release do not imply review completion.

When completing a requested review issue in review mode, require its latest request's exact candidate and named reviewer. Keep existing current-candidate and own-active-generation guards. Ordinary completion/yield stays available to release blocked work. A conflict leaves the possession intact. The current request projection is subject to the viewer's access to both current roots and both original events; select canonical latest before filtering. Never reveal a hidden successor's ID, hidden review peer or count. If determining supersession would expose a hidden replacement, omit that request from the projection for that viewer. Request status is advisory; issue readiness, verdicts, and approval policies retain their existing owners.

A fulfillment has its own third native completion event. Select the latest later matching candidate/review issue/named-reviewer completion before applying its read visibility. A hidden matching completion has exactly the same public behavior as no visible fulfillment, including request status, desk membership and clipping/counts, queue, context and error shape. Never substitute an earlier visible completion. Test a request and candidate in P, a later completion after both issues move to private Q, and both issues moved back to P, comparing the P-only observer with a no-fulfillment control.

The shared read item exposes request_id, candidate_id, review_issue_id, reviewer_id, status, reviewer_holds_active_lease, identity, source_issue_id, completion_event_id (the candidate submission's native evidence pointer) and source_work_context_url. Groups use items, visible_total, returned, limit and clipped; the desk limit is 20.

Amended 2026-11-22 by [the requested-reviewer decision](decisions/2026-11-22-requested-reviewer-verdict.md) (D4): the shared read item also carries `fulfillment_event_id` and `reported_verdict`, after `reviewer_holds_active_lease`. When the status is `fulfilled` they are the fulfilling completion selected above and the verdict its native report states (`PASS`, `PASS-WITH-NOTES`, `HOLD`, `BLOCKED`, or null for a report without one); otherwise both are null. The fulfilling completion is the requested reviewer's own, on the request's review issue, about its exact candidate, so no other account's review moves either field, and the newest such completion wins. This supersedes two sentences of this specification. "Request status is advisory" stands for the status, but the conductor recipe now gates on the request row's `reported_verdict`. "Keep the queue's verdict and request-status fields separate" no longer holds for the request row: it carries its own reviewer's verdict beside its status. The queue row's `review_state` and `latest_review` are unchanged and stay separate from it. Unrequested reviews, issue readiness and approval policies are unchanged, and the field grants nothing.
